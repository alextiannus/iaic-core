# Durable bounded tool plans

AgentRuntime defaults to maxBatchCalls: 1. A host may explicitly set an integer from 2 through 8. Include this setting and the deployed code/Skill revision in the Task version contract; changing a running Task's policy is not an implicit migration. The standard provider receives this bound, advertises multiple-call support, validates every returned tool name and JSON object, and returns a batch only within that bound. Finish, wait and delegation must remain separate responses; mixed controls are rejected with usage retained. Single-call/default provider behavior remains unchanged.

The Runtime records one immutable action_batch event before preparing any action. It executes the finite list sequentially through the same dispatcher, current Capability/Permission/Mandate/parent/grant checks, call budgets and original outcome verifier. This is not parallel side-effect execution or another Runtime. Additional batch steps consume tool budget, not new model requests; provider usage is charged for the original response once. Dependent steps should be planned only after reading earlier results, not by inventing future response references.

Each prepared call atomically binds a unique task/action_ref (batch UUID plus index) in migration 014. Rebuilding the pending plan uses original call receipts. Succeeded steps are not dispatched again. Unknown or still-running effects pause the Task before later actions; after trusted reconciliation of the original call, the pending plan can continue. Failed steps abandon unexecuted actions and return control to ordinary model planning. Executor recovery marks a prepared-but-undispatched call failed under the existing Harness rule; the batch does not hide it with a new call ID. Cancellation stops remaining work; prior effects remain responsibilities to reconcile or compensate.

Every step revalidates existing context and its own current authority. A scope rejection closes the pending plan; other interruptions retain the normal Task wait behavior. A batch larger than remaining tool budget is rejected before any action. If the runtime call ceiling is reduced while work is pending, it pauses rather than crossing that ceiling. Batched writes are not one atomic transaction; there is no automatic rollback, compensation, blind replay, or promise that a failed operation had no external effect. Those decisions require original domain evidence and capabilities.

The default PostgreSQL TaskStore supplies migration and atomic receipt binding. Custom Task stores/executors need equivalent action_ref support, and custom context adapters need current-history revalidation before enabling this feature. The host must not bypass these ports with a batch-enabled custom provider.

Integration evidence covers finite sequential execution, model/tool budget distinction, current permission rejection, unknown-effect reconciliation across service reconstruction, interruption after durable preparation, failure abandonment and cancellation. The interruption fixture is not an OS process-kill test; broader process-crash/real-model evidence is recorded separately. A passing batch integration test is not complete Note 30 acceptance.
