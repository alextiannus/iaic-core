# Monetary invoices, payment and refund operations

This independent headless module stores monetary facts, not platform-issued allowance units or LLM provider tokens. `PostgresPaymentStore({pool,namespace})` is the replaceable default persistence adapter. It owns immutable invoice snapshots, payment/refund intents and append-only operation events. Amounts are positive integer strings in the currency's minor unit, up to 30 digits; floating point amounts are rejected. The host defines currency precision, prices, taxes and quote validity.

`Payments({store,provider,resolveScope,authorize,resolveInvoice,timeoutMs})` supplies issue/read, charge/refund, operation get/history, reconciliation and cancellation before dispatch. `resolveInvoice(sourceId,{actor,scopeId})` must return a confirmed source with matching sourceId/scopeId, currency and amount. The public issue capability accepts only sourceId. Invoice creation is bound immutably to that source. It is not a tax invoice renderer, general ledger, subscription catalog or application order database.

`createPaymentCapabilities` exposes eight ordinary shared capabilities. Current authorization receives the action and input so hosts can distinguish read, invoice issue, payment, refund and reconciliation permissions. Scope comes from the authenticated host, never model input. Charge/refund use the existing Dispatcher callId as the request key. Actions remain subject to the application's Permission/Mandate/Policy and audit context; this module does not invent financial consent from model intent.

One full charge is admitted per invoice while a charge is prepared, running, unknown or succeeded. A definitive failed attempt permits another explicit request. Refunds reference a succeeded payment from the same invoice; confirmed and reserved/unknown refunds cannot exceed that capture. Invoice locking serializes concurrent admissions. Request keys bind the exact original intent; they cannot be reused to change the amount or invoice. Invoice reads show paid/refunded/netPaid amounts and operation states; unknown money is never presented as confirmed.

## Provider ports

The provider implements `charge(operation,{actor,signal})`, `refund(...)`, and `query(...)`. The operation carries a stable id, scopeId, invoiceId, paymentId for refunds, kind, amount and currency. The host maps that id to the provider's idempotency key and resolves its own customer/payment-method identifiers and credentials. Never place raw card details or secrets into a Capability input or operation result.

The normalized provider result is `{operationId,status,amount,currency,providerRef?}`. Status is `succeeded`, `failed`, or `unknown`. Success requires an immutable provider reference; id/currency/amount must match the original intent. Failed means definitive terminal non-execution/failure, not timeout, a missing lookup result, a transport error or a still-pending payment. Query must return unknown if a concurrent request could still be accepted. Provider adapters must verify their own authentication, webhook/query origin and evidence. Core records stable references, not arbitrary provider payloads.

`createHttpPaymentProvider({baseUrl,resolveHeaders,bindings,idempotencyHeader,fetch,timeoutMs})` adapts an existing JSON payment API through explicit charge/refund POST and query GET mappings. Each binding provides `request(operation,context)` and `project(body,context)`. It reuses Core's bounded HTTP importer and restricts calls to the configured service prefix, with no redirects or automatic retries. Both POSTs carry the original operation id in the provider's configured idempotency header. Configure its real contract; this generic adapter does not claim Stripe/PayPal compatibility or infer endpoints. A fake in-process adapter is used only by tests.

## Recovery and boundaries

The database records the intent and atomically claims dispatch before invoking the provider. A crash after claim, lost response, timeout, cancellation during execution, malformed evidence or provider error leaves running/unknown work reserved. Calling charge/refund again with the same key returns the existing operation without dispatching it again. Reconciliation only queries the provider. It can confirm completion or definitive failure; it never repeats a charge/refund. Terminal evidence is immutable. A failure to save a result also leaves the original persisted intent available for query.

Undispatched prepared work can be cancelled; dispatched work requires query or, after capture, a separate refund. Whole-process crash can leave `running` until explicit reconciliation. There is no background reconciler, provider webhook verifier or automatic refund/compensation policy in this first adapter. A never-accepted remote request may remain unknown if the provider cannot prove definitive non-execution; do not free its reservation speculatively.

The real PostgreSQL example exercises a lost capture response, service reconstruction, query reconciliation, no duplicate capture, concurrent refund limits and current revocation. Additional checks cover immutable scoped invoices, large integer amounts, one dispatch claim, cancellation, mismatched evidence, timeout and HTTP idempotency mapping. No real payments are made. This establishes foundational state/adapter behavior, not production payment-provider acceptance, financial regulatory compliance or the full Note 30 acceptance criteria.
