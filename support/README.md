# Support issue lifecycle (additive Basic module)

SupportIssues connects user reports to engineering work and verified resolution. It does not implement an autonomous code writer, new scheduler, business recovery or deployment engine. Reuse Tasks for engineering work, Observation/ReleaseManager for trusted runtime evidence and Notifications for transport. This source change is unreleased until packaged, independently verified and published.

Host ports restore current identity and authorization on each call. `scopeId` is an application-defined tenant boundary; `subjectId` is the authenticated reporter. Reports only contain bounded summary and optional task/request/release/error references. User text and references are untrusted; they are not instructions to Platform AI or proof of an incident. The host handles consent, redaction, attachment policies, source verification, retention, rate limits and automatic error ingestion. No caller-supplied actor, notification destination or verdict is trusted.

`report` is idempotent by namespace/scope/reporter/requestKey. Same-key different-content submissions fail. Different reporters keep separate issues even if symptoms match; cross-user deduplication and privacy-safe subscriptions are future work. `list` shows the current reporter's issues; `queue` requires manage permission. `get` checks reporter ownership or current manage permission. Hosts must deny manage access by default.

States: received → triaged → fixing → verifying → resolved → closed. Verification may return to fixing; resolved/closed can reopen, then return to triage. Reporter may close or reopen only their issue. Engineering changes require manage permission. Each change has an expected revision, atomic history, and conflict rejection; after lost acknowledgement read the issue/history instead of blindly applying again.

Resolution accepts an evidence ID, never a caller verdict. Trusted `resolveResolution` must verify current deployed release, health and regression, and bind confirmed:true, scopeId, issueId and expected revision. It returns deployed:true, healthy:true, regressionPassed:true, releaseId and verificationId. The service rechecks current authorization after resolution and stores only immutable references. A host must implement this check from trusted deployment/evaluation systems, not relay JSON from the model or end user. Source revocation/retention remains host policy.

`notify` queues an existing immutable event to the original reporter through Core Notifications, using `support:issueId:revision`. Replays reuse that event identity; no notification is sent by state mutation itself. A worker can recover after interruption by enumerating issue events and enqueueing them with this stable key. The host configures an authorized notification actor and logical `support` channel, maps to the user's original inbox/channel, schedules notification ticks and verifies delivery receipts. Queueing is not delivery, delivery is not human reading, and unknown delivery is reconciled rather than blindly retried. Historical messages carry their original revision and must not be shown as the current status after reopen.

Initialize the additive PostgreSQL schema through the host's migration lifecycle. `createSupportCapabilities` provides report/get/list/queue/update/notify via the normal dispatcher with input schemas and read-history authority revalidation. No table in the existing task, notification or observation modules is changed.

Remaining scope: host capture/UI, trusted Platform Agent identity, engineering-task linking/claiming, automatic event collection, cross-reporter deduplication, notification scheduling, deployed release adapter and actual user acceptance. This module does not claim these are configured in 12Eat.

`list` and `queue` return bounded pages (default 50, maximum 100). Pass the last issue's `id` as `afterId` until an empty/short page; ordering is stable by UUID, not creation time. Restart a scan to discover concurrent reports inserted before the cursor. Tenant/reporter authorization applies independently to every page. Notification admission rechecks the caller after the asynchronous sender resolver.

`SupportEventConsumer` is a trusted host worker port for durable engineering handoff
and notification admission. Each independent consumer acknowledges individual events
only after its delivery port succeeds. A failed callback remains pending, including
when its external effect succeeded but the acknowledgement was lost. Delivery ports
must use the supplied stable `requestKey` to deduplicate or query that effect before
retrying. This is not a task executor and grants no code, repository, or deployment
authority. Do not expose `pendingEvents` directly to untrusted callers. The host must
restore current engineering authority and scope before exposing any report content.

## Candidate.115: observations and original-reporter follow-up

Implements the bounded contract in `IAIC-FB-20261005-001A2B`. `SupportIdentity.sourceKind` is restored by the **trusted Host**, not accepted from capability input. Its values are `end_user_reported` (the backward-compatible default), `user_assistant_detected`, `business_ai_detected` and `system_observed`. Bind distinct, stable subject IDs to humans and agents; do not resolve an agent using the affected user's identity. `PostgresSupportStore` exposes the effective kind on every issue, including legacy user reports. A source-less legacy report is interpreted as a user report; Hosts must audit/backfill any historical machine reports rather than relabel them from guesses.

`support.observe({sourceId})` calls the current-authorized `resolveObservation(sourceId,{actor,identity})` Host port. It must confirm the exact scope, reporting subject, source kind and immutable source ID and return a bounded summary, plus optional Task/Request/Release/error/agent/affected-subject/evidence references. Agent observations require an agent ID. Only these fields are stored, always with `assessment: candidate`; confirmation authenticates the source binding, not a verified bug or repair. Source keys deduplicate concurrent and restarted detection independently of retry input; changed content under one source key conflicts. Source IDs are at most 480 characters and immutable; corrections use a new source revision. The namespace/scope/reporter still isolates separate observers. `affectedSubjectId` grants no reads and is not a notification destination. Agent identities must use observe, and cannot use report to claim human provenance. Expose observe only in the intended runtime contexts and apply rate limits/redaction at the Host boundary.

`createSupportResolutionConsumer` composes the existing event consumer with Support.notify. **A Host enabling user-report resolution must schedule it**, with a stable consumer ID and a current, scope-bound engineering identity from `resolveActor`. Every committed resolved event for an end-user report stays pending until notification admission succeeds. Crashes after enqueue recover with the same notification key. Other events are acknowledged; agent-detected resolutions do not automatically notify affected people. The Host may implement a separately authorized impact notification policy. No automatic code execution, new engineering Mandate or deployment authority follows from an observation.

`SupportFollowUp.get` / optional `support.follow_up` returns separate admission, delivery and read states for the original issue revision. It reads the existing Notifications authority by exact issue/revision/recipient/channel/scope; no second delivery state machine is introduced. `not_verified` means there is no verified human read evidence, not that the human definitely has not read. A reopened issue keeps its previous notification facts and reports `historical: true` and the current issue revision. The original Support report/get/list/update/reopen behavior is preserved.

`SupportFollowUp.recordRead` / optional `support.record_read` accepts only an evidence ID, requires current manage authority and already verified delivery, and calls trusted `resolveRead`. The resolver confirms scope, issue/revision, original recipient, notification ID and read time from the authenticated receiving channel (for example an Inbox receipt); it must not relay a model/user verdict. Receipts are append-once, idempotent for the same fact, and conflicting evidence cannot overwrite them. Get and recordRead recheck current authority after asynchronous ports. Notifications with unknown delivery still use Notifications.reconcile and never replay because of a read request. Channel delivery and read evidence are not supplied by Core itself.

### Migration and rollback

Initialize the additive `iaic_support_read_receipts` and `iaic_support_event_retries` tables through the normal Host migration process; original issues, events and notification tables are unchanged. Existing custom stores need `readReceipt`/`recordRead` for read evidence and `deferEvent` with fair retry-aware `pendingEvents` for the resolution consumer. Generic SupportEventConsumer keeps its existing immediate-retry default; the resolution consumer requires durable deferral (default 30 seconds, configurable 1–3600). Failed delivery attempts rotate behind older untouched work even when the polling interval exceeds the delay. Admission succeeded but acknowledgement failed can reconcile immediately by the original key. A failed retry-store write never acknowledges or discards the event. Stop old Support workers before enabling machine-origin records: candidate.114 does not understand their notification policy. Rollback by disabling observation/follow-up entrypoints and their consumer while retaining all source records, event receipts, notification unknown states and read evidence. Do not process machine-origin records through an old user-only notifier. No raw logs or private conversations are added to this module.

The installed-package example and regression suite exercise actual PostgreSQL, source isolation, forged bindings, revocation, crash-after-admission, unknown delivery, independent human read and reopened historical status. Host resolvers/channels are synthetic fixtures, not 12Eat production adoption or an autonomous engineering workflow. The broader conversational classification/clarification and repair-agent work described in historical notes is outside this feedback's bounded implementation.

Code Review regression also verifies permission revocation during the final issue read: Support rechecks current scope, subject, source kind and required authority after storage reads before releasing results. See `support/REVIEW-001A2B.md`.
