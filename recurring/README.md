# Recurring tasks

`RecurringTaskStore` owns one PostgreSQL table of fixed-interval rules; `RecurringTasks` materializes each due occurrence through an injected idempotent `scheduleOccurrence(actor,{requestKey,dueAt,input})` port. ImmediToday connects that port to existing DeferredTasks. Task execution, model configuration, allowance, tools and cancellation after Task admission remain in the existing Runtime. No calendar UI, cron parser, message broker or second Runtime.

Public operations: `create/get/list/change`. Creation fixes a request key, explicit timestamp, interval (60 seconds–365 days), optional occurrence count (1–1,000,000), and task input. Count null means ongoing. Identical replay returns the same rule; changed parameters conflict. All operations resolve the host's authenticated scope. App adapters supply actor restoration, current task validation and worker enablement.

Occurrence sequence starts at zero. Missed intervals coalesce to the latest due occurrence; skippedCount records earlier slots that were not materialized. A finite rule also coalesces to its final slot after downtime, then completes. Fixed intervals are elapsed seconds, not local calendar days or DST rules. Occurrences are independent Tasks and may overlap. A completed rule means all remaining scheduled slots were materialized or explicitly counted as skipped, not that Tasks succeeded. Inspect lastIntentId and its linked Task for the actual result. Earlier intents remain in DeferredTasks under `recurring:<rule-id>:<sequence>` keys.

Each claim persists its pending sequence before calling the host. A lost response or lease uses the identical sequence/key/input/date; no new occurrence is chosen until that receipt is resolved. Three bounded attempts block the rule. Explicit `change` to active retries that same pending occurrence. The host must reserve the occurrence key prefix against public creation and guarantee immutable idempotent scheduling. ImmediToday reserves `recurring:` on its DeferredTasks instance; the code-only internal scheduling option is not read from HTTP/MCP JSON.

Lifecycle changes use expectedRevision. Pausing/resuming/cancelling prevents future materialization; existing intents and Tasks keep their own lifecycle. A live claim or unresolved occurrence rejects pause/cancel with 409 until receipt recovery. Cancellation is terminal. No automatic cascade across modules is claimed. Current authorization is checked again before scheduling and before actual Task dispatch. Resuming after a long pause uses the same coalescing policy. Global worker disablement prevents new claims; work already admitted may finish.

HTTP application adapters: `/api/assistant-recurring-tasks` for POST create / GET list or read, and `/api/assistant-recurring-tasks/state` for POST state changes. `recurringTools` exposes identical methods to MCP. Apps supply their own interaction and presentation.

This is the fixed-interval base capability. Calendar/timezone expressions, arbitrary external event subscriptions, dependent/non-overlapping recurring work, delegated Mandates and end-to-end retention remain unfinished. Tests: `test/iaic-recurring.integration.test.js`; independently installed example: `examples/core-recurring`.


## Default Agent scheduling composition

`createAgentTaskSchedules({deferredStore,recurringStore,dispatcher,tasks,resolveScope,restoreActor,authorize,isEnabled?,logger?})` returns the existing `{deferred,recurring}` services. Stores are initialized by the host. It accepts `{capability,input}` as scheduled task input and only targets registered Agent capabilities through the shared dispatcher. The same current identity, schema, capability authorization and host scheduling policy are checked when accepting work and before Task admission/receipt lookup. Model selection, Mandates, Agent identity, allowance and Task tools remain owned by the configured Runtime; this adapter supplies no alternate execution policy.

The deferred start uses `deferred:<intent-id>` as the dispatcher call ID. Recovery looks up the original scoped Task through `tasks.findRequest` and compares its exact capability/input before accepting it. Recurring occurrences use the existing internally reserved `recurring:` intent keys. The host must also reserve the `deferred:` Task key prefix at its public Task entrypoints; do not forward arbitrary caller IDs in this namespace. This is a trusted composition API, not a public authentication boundary. Scope resolution/restoration must map current authenticated owners to their original application/assistant/subject binding.

The host owns `start/stop/tick` lifecycle for both services and the Runtime. One-time intents use `deferred.schedule`; periodic rules use `recurring.create`. Each periodic input remains immutable; changed schemas or revoked authority block future admission. Conditions, timezone expressions, overlap exclusion, nested delegation/scheduling policy and cascade cancellation are not added. This composition currently rejects conditional triggers; the lower-level DeferredTasks ports remain available for that separate integration.

`examples/core-recurring-monitor` demonstrates a scheduled Platform task using ReleaseMonitor. Two separate worker processes materialize an occurrence, lose a successful Task-start acknowledgement, recover that same Task and execute a single monitor/rollback. The schedule's completed state alone is not used as proof: the example checks the linked Task outcome and release history. This is deterministic synthetic evidence and orderly process replacement, not a paid-model or SIGKILL monitoring test.
