# Application-configured AI jobs

A minimal headless host registers personal and organization-shared work after Runtime initialization. One work capability composes existing Skills, sourced Knowledge, Memory, Workspace, model settings and platform allowance interfaces. The fixture model reads actual tool results and produces a checked draft. Alice has separate personal work in two organizations; Bob can access the shared editorial job's resources but not Alice's personal workspace.

The application stores definitions in a temporary JSON file, reloads them and reconstructs the service before executing queued work. This exercises stable configuration revisions and a Task actor codec that preserves user, organization and job selection. It is service reconstruction, not an OS crash. Updating a job's purpose changes its hash and invalidates an old task binding. Existing work is never rebound silently.

`shared`, `skills`, `knowledge` and `tools` are this example application's configuration keys, not a prescribed Core schema. The application maps authenticated membership to resource scopes and applies tool selection through ordinary Capability authorization. Registry registration itself grants no authority. Model preference persists through AssistantSettings; default system model resolution and platform allowance use AssistantModels/TokenLedger. The 56 charged units per task are fixture platform units, not provider tokens or money.

Run `npm run verify:core-package` with an isolated `SUBMISSION_TEST_DATABASE_URL`; it packs and installs Core outside the application repository before running this consumer. No ERP, real provider, UI, public endpoint or production credentials are used. All synthetic schemas and files are removed. The example demonstrates configuration and composition, not model quality or a completed application management interface.

The same host also composes `createAgentSessions` and `createAgentDeferredTasks`. A model reads a pinned Session and schedules a follow-up; the Session closes, services rebuild, and the future Task produces a draft using the same job resources and Session source. The closed Session then projects both completed Tasks and the exact current artifact reference. Before future admission the host changes the model preference; the child uses that current model while its parent remains pinned. The fixture parent consumes 21 platform units and future Task consumes 56. The elapsed timestamp avoids a wall-clock sleep in this deterministic example; dispatch is withheld until service reconstruction.

The scheduler preserves the initiating member plus organization/job, while Session/resource sharing follows application scope. The example does not silently make all member Task histories public. These helpers compose existing modules; there is no second scheduler, runtime, configuration database or UI. The host owns configuration distribution, current authorization and reference validation. New executable behavior follows development and release.

An external MCP client also uses the configured job. Direct Workspace/Skill calls produce the same JSON values without hosted model inference. Optional `job.work` admission uses the same Session-aware entry and stable request key as SDK callers; the client observes queued/completed Task state through `my_read_agent_task` and reads its exact artifact. Session association remains singular across entrypoint replay. The MCP SDK is an optional peer for Core and is installed by the independent verifier before this example runs.
