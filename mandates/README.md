# Mandates

An independent persistent authorization module. A Mandate expresses what the owner lets an Agent do autonomously; it does not confer an account permission. Application capability authorization, domain rules and model/allowance policies remain mandatory. No UI, approval wizard, second Runtime or delegated-identity service.

`MandateStore({pool})` owns `iaic_mandates`. `AssistantMandates({store,resolveScope,authorizeGrant,sourceFor,clock?})` exposes grant/read/list/revoke/checkTask. Trusted scope is application/assistant/subject. The host authenticates it on every access, authorizes grants separately and supplies source attribution. Model-provided source/owner fields cannot replace these ports.

Grant terms are immutable: stable requestKey, one capability, a nonempty unique tool list, explanatory purpose and an explicit ISO expiry with timezone. Fractional seconds up to nine digits are accepted and normalized to JavaScript millisecond precision (sub-millisecond digits are truncated). Same key/terms returns the original record, including after revocation/expiry; changed terms return 409. Tools are order-normalized. Past expiry is readable but never authorizes execution. Purpose is context, not an enforced semantic goal or resource filter. The host must use current resource ACL and task-specific capabilities for those constraints.

Revoke is permanent and idempotent, preserving its first timestamp. A new authorization requires a new key/ID; old tasks cannot substitute it. Records and source attribution are retained; no erase/archive policy or independently signed audit is provided. List includes inactive records and pages by ID; it is not a snapshot of concurrent insertions.

Task input may explicitly reference `mandate:{id}` and must then declare `allowedTools`. `checkTask(actor,{capability,input,tool?})` rechecks current ownership, expiry/revocation, capability and tool subset. AgentRuntime accepts a `mandates` port and checks it before admission, inference, after responses and before tool intent preparation. Bound tasks fail closed when the port is absent. Model tool discovery is narrowed to the bound task's explicit tools. Regular task authorization is still checked separately. In-flight operations may complete after revocation; their usage/results remain accountable. Revocation does not roll back effects. Read and cancellation remain available; resume/new admission against the revoked reference fails.

ImmediToday grants only `assistant.run` with registered Assistant tools. HTTP `/api/assistant-mandates` GET list/read and POST grant, `/revoke` POST, and the corresponding MCP tools share this service. Grant/revoke are external owner operations, never internal Assistant tools. Immediate, deferred, recurring and conditional tasks may reference a Mandate; scheduled admission also checks it. Tasks without a reference retain their explicit per-request authorization, rather than silently inheriting a standing grant.

This first implementation supports a persistent owner-to-Assistant authorization reference, not delegation chains, A2A, service-principal provisioning, cumulative per-Mandate budget pools, fine-grained data filters, automatic mandate discovery or renewal. Existing platform allowance/Task budgets apply unchanged and BYOK behavior is unchanged. See focused Core tests `test/iaic-mandates.integration.test.js`, separate application tests `test/ai-native-mandates.integration.test.js`, and independently installed `examples/core-mandates`.
