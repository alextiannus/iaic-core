# Task completion triggers

`TaskCompletionTriggers` observes an existing durable Task through an injected `readTask(actor,id)` port. `taskFollowupTool` adapts its public `followUp` method to MCP. The trigger module owns no Task tables, second queue, message broker, Runtime or UI. It reuses DeferredTasks for durable intents, cancellation, leases, retries and Task receipt recovery.

A trigger is `{kind:'task',taskId,on:'succeeded'|'finished'}`. `succeeded` requires the existing Runtime's success state. `finished` explicitly allows succeeded, failed or cancelled. Queued/running/waiting sources do not fire. A terminal non-success source blocks a success-only subscription; it cannot later become successful under the original Task lifecycle. Use a new source or cancel that intent rather than rewriting its condition. Already terminal sources can be observed after registration. This is durable state-based completion observation, not a general event bus or real-time delivery guarantee.

`normalize` validates current source access and canonical identity. `check` returns null while pending, a small `{kind,taskId,status,completedAt}` receipt when matched, or an explicit error for revoked/invalid/unmatched sources. Source content is never copied into a receipt. The host must return authoritative immutable terminal state with current authorization. `followUp(deferred,actor,{requestKey,trigger,input})` pins `input.sourceTaskId`, uses the existing immutable schedule key and a fixed earliest eligibility timestamp. No model is called to register or check a condition. ImmediToday requires explicit allowedTools.

DeferredTaskStore owns the trigger/reference receipt with its intent. It saves the receipt before Task creation. Pending condition checks release their lease, poll no sooner than five seconds later and do not consume failed-dispatch attempts. Claim ordering considers next eligibility so a pending source does not monopolize unrelated ready work. Loss of the task-start response uses the existing stable `deferred:<id>` request key. Current Task identity/model/allowance controls still apply when execution starts. Retry and cancellation retain the existing admission/uncertainty rules.

The follow-up is a distinct persistent goal, not another Agent spawned inside the source loop. It cannot recursively create more subscriptions through its model tools. Source IDs must already exist; the application contract rechecks source access on subsequent model turns. A stopped source's artifacts and state remain evidence; they do not confer new authority or prove general semantic quality. Use the configured `my_read_agent_task` capability for current artifact references; deleted/revoked artifacts disappear from its view.

ImmediToday exports POST `/api/assistant-task-followups` and `my_follow_up_assistant_task`. Existing scheduled-task APIs query/cancel/retry the returned record. GET `/api/assistant-task-reference?taskId=...` and MCP/internal `my_read_agent_task` share the capability dispatcher. No notification/calendar/workflow UI is added.

Limits: one source Task, one follow-up; no recurrence, arbitrary webhooks, multi-source boolean rules, dynamic goal templates, organization event subscriptions or full Mandate/delegation system. Long chains remain subject to current source-authorization cost and Context/Runtime limits. Production completion observation across a server restart is not claimed by local worker-replacement tests. Focused tests: `test/iaic-task-triggers.integration.test.js`; independent example: `examples/core-triggers`.

Compatibility: conditional rows put the real earliest time in `trigger_not_before` and fence their legacy `due_at` at year 9999. New claimers use the real eligibility; old time-only claimers cannot accidentally start them on rollback, including expired claims or retry rows. Time-only rows keep their previous format. This is storage compatibility, not a user deadline or scheduled execution time.

`EventTriggers` provides one-time conditions on a scoped immutable event key. `triggerRouter({task,event})` composes handlers using ordinary injected methods. See `../events/README.md` for publication provenance and limitations. Existing Task completion semantics are unchanged. Event follow-ups use the existing DeferredTasks lifecycle and pin sourceEventKey; they do not infer trusted business outcomes from user-provided signals.
