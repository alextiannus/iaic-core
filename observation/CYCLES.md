# Persistent monitoring cycles

`PostgresMonitorCycles({pool,namespace})` stores original monitoring-cycle keys, prepared assessment/target snapshots, protection decisions and final results in its own table. Initialize it before use. `PersistentReleaseMonitor({monitor,store,resolveOwner,authorize})` composes the existing ReleaseMonitor, not a new scheduler or Agent Runtime. The host maps authenticated identities to stable owner strings and explicitly authorizes run/recover for a channel. Owner and namespace are trusted partitions; callers never choose them.

`run(actor,{channel,requestKey})` admits a unique owner/key bound to one channel. Only the creator executes the monitor. The monitor's trusted beforeProtection hook saves its complete collection/assessment, target manifest/channel revision and whether host configuration enables protection before any protective action. A storage failure prevents protection. A bounded snapshot (at most 1 MB JSON) is integrity-digested, and normal completion saves the immutable original result. Reusing a key never restarts collection or protection, even if availability, policy or channel selection changes. Use a new explicit key for a genuinely new scheduled cycle.

`recover(actor,{channel,requestKey})` locates the saved original binding. Completed results pass current monitor/assessment history checks. A prepared assessment-only result can complete without more collection. A prepared protective cycle uses the original protectionResult lookup; only a confirmed original event completes its journal. A missing event stays unknown, and recovery never calls protect. Current cycle and monitor/observation/release history policies remain necessary even when the original operation was authorized. The saved flag is historical intent, not new execution authority.

`createMonitorCycleCapabilities({cycles,prefix:'monitor_cycle'})` exposes run/recover as idempotent writes using these explicit stable keys; recovery may write the final journal result. They use the shared dispatcher and current revalidation. A repeated completed key returns a historical cycle result, not a new current-channel observation. A changed channel under the same owner/key conflicts. Different owners cannot read each other's journal. Unknown failures carry monitorCycle binding and outcomeUnknown; recover does not require the caller to retain an internally generated assessment ID.

An actual worker SIGKILL test kills the process after the release transaction commits but before the monitor gets its acknowledgement. A reconstructed service finds the prepared binding by cycle key, confirms the original event even after assessment aging and completes the cycle without another rollback. Other PostgreSQL tests cover repeated/conflicting keys, owner isolation, current revocation, unresolved started cycles, and assessment-only completion acknowledgement loss. The installed Docker release example uses these cycle capabilities.

## Remaining interruption boundaries

A started cycle without a saved assessment remains unknown; this implementation never resets admission or guesses the old worker is dead. Likewise, a prepared cycle without a visible rollback receipt remains unknown, including interruption before the protection call. There is no automatic worker, lease takeover or permission to blindly repeat protection. Host workflows can query/reconcile known cycles and decide when a separately keyed new observation is appropriate. Snapshots and original results are retained without an automatic retention policy. Generic external side effects, cloud traffic rollback, production telemetry completeness and full Note30 acceptance are not established by the database SIGKILL test.
