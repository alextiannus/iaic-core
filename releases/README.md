# Release manifests and version selection

This independent module binds implementation/resource version references to evaluated candidate records and provides stable/canary selection, stop checks and rollback selection. The default PostgreSQL store retains immutable candidate content and release decision history. It does not deploy code to cloud providers or replace a Runtime's execution state.

`ReleaseManager({store,evaluations,policies,authorize,resolveCohort})` requires trusted host ports. `evaluations.get(id)` loads retained evaluation evidence, for example from FileEvaluationStore. Both capability and regression policies must pin datasetDigest, graderRevision, environmentRevision and repeats; they optionally specify thresholds and a baselineId. Policy configuration is copied privately at construction and included in candidate evidence. The registration request cannot choose or weaken it.

`register(actor,{manifest,evaluations:{capability,regression}})` checks both suites against the candidate's implementationRevision, the frozen suite pins, outcome gates and any configured baseline. Each manifest has `id`, `implementationRevision` and `versions` containing prompt/model/skills/tools/knowledge/harness references. Extra JSON artifact metadata is allowed. Candidate content, manifest digest, policy and evaluation digests are persisted together. Reusing an ID with different content conflicts; registering the same stopped record does not re-enable it.

Version references must resolve to immutable host artifacts/configuration. A fixed label pointing at mutable content does not become reproducible just because it is in a manifest. The host's loader must verify artifact revisions/digests and keep old versions available. Remote model providers may not expose immutable weights; record available model/provider configuration and observed revision without overstating reproducibility. No credentials belong in public manifests.

`setChannel(actor,{name,stableId,canaryId?,percentage?,expectedRevision})` creates at revision zero or atomically replaces the observed revision. Both targets must be registered and enabled. `resolve(actor,name)` chooses a deterministic cohort bucket from the host's `resolveCohort(actor,{channel})` value and returns the chosen manifest plus a pinned reference. Promotion sets the candidate as stable. Rollback sets a previous enabled candidate as stable, using the current channel revision. `channel(actor,name)` reads settings; `history(actor,page?)` reads ordered decisions and actor references.

`stop(actor,id)` permanently disables that candidate ID. A stopped canary falls back to the enabled stable candidate; a stopped stable candidate blocks selection unless another enabled candidate is selected. `check(actor,{releaseId,manifestDigest})` rejects stopped or mismatched bindings. Changing channel routing alone does not rewrite an existing binding. Wire check into current admission/execution policy and use manifest.implementationRevision as part of Runtime version binding. A selection or check is not a permanent permission lease and cannot undo already completed actions.

`createReleaseCapabilities({releases,prefix?})` exports register/configure/stop/resolve/check/channel/history through the shared Dispatcher. The host supplies current identity and authorization for each action; no mandatory Platform/User/Business role classes are introduced. Low-level store methods are trusted infrastructure ports and must not be exposed as unauthenticated registration bypasses.

The default store serializes mutations per namespace and appends decision events in the same transaction. Snapshot digests detect content mismatch; they are not signatures against a malicious database administrator. Existing code deployments, environment readiness, resource loading, production observation, automated rollback policy and independent real-model acceptance remain integrations to complete. Routing a manifest is not evidence that a cloud deployment occurred.

`examples/core-releases` composes actual evaluation files with PostgreSQL candidates and demonstrates canary selection, stop and rollback. Its two suite bindings deliberately use one small fixture dataset to demonstrate wiring; this is not a substitute for separate capability/regression or held-out application datasets. No production deployment or real model evaluation is performed by the example.
