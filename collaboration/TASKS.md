# Persistent delegated Tasks

`DelegatedTasks({grants,ledger,modelPolicy})` connects the existing cross-principal grants and shared budgets to AgentRuntime. Supply it as `authority` when constructing the Runtime. This does not introduce another task store or executor.

Issue a grant through DelegatedCapabilities with the ordinary terms plus `task: {capability, input, budgetId}`. The grant's input is an exact approved Agent input with explicit allowedTools, all within the grant tool ceiling and the Agent's declared tools. Nested delegation is currently rejected. The application's authorizeGrant port must approve the complete task, both identities, payer, scope, deadline and budget binding; models cannot select these terms themselves.

Create the payer's budget with `delegationExecutorKey(delegatePrincipal)` as an allowed executor. This canonical principal key avoids ambiguity across identity domains. The grant stores the budget ID; the ledger enforces account ownership and reservation limits. `modelPolicy({actor,task,model,terms})` returns trusted `{mode, policy: {maximum, price}}`. The Runtime's ordinary model resolver supplies the executor's unmetered provider, retaining its pinned model identity. DelegatedTasks wraps it with the existing meteredModel, injecting the grant's payer and budget. Already metered providers are rejected to prevent double billing; hosts must resolve provider credentials and mode consistently. This API does not configure credentials or allow silent SYSTEM/BYOK fallback.

`authority.submit(delegateActor, grantId)` submits through the shared Dispatcher using a reserved stable request key. AgentRuntime binds the grant ID and immutable digest on the persistent Task and its created event. Repeated submission returns the original Task; changed input or authority cannot occupy the same Task key. Missing authority adapters fail closed on admission and execution. After reconstructing the Runtime, the same Task continues under the original grant, model identity and budget.

Execution rechecks both principals' Agent authority. Each inference checks the current grant before the existing model gateway reserves payer units. Tool execution and result polling recheck both principals' tool permissions and the host's domain input constraints, then atomically consume the grant call ceiling before dispatch. The grant journal preserves the actual Runtime effect key. Historical successful tool inputs are also rechecked before context assembly, while existing ContextAssembler source revalidation still governs result content. A model finish continues to require the Agent capability's original trusted outcome verifier.

`authority.cancel(issuerActor, grantId)` revokes the grant and transitions its exact bound Task to cancelled using the existing Task store. It checks the issuer's current grant-control policy and the immutable Task binding, so executor permission revocation does not prevent cancellation. Revocation/cancellation prevents later admission; already dispatched external effects or inference must still finish or reconcile in their original records. This is not compensation or an immediate hard kill of a provider request. If the host crashes after revocation but before Task cancellation, repeating cancel completes the transition; Runtime checks already prevent further execution.

The grant journal is supplementary: if outcome recording fails after Task settlement, it can retain admitted evidence. The Task/call history remains authoritative for that effect. DelegationArtifacts now provides explicit cross-principal input/output sharing and result projection (see ARTIFACTS.md). Parent/child scheduling, automatic cancellation sweeps and failed-child takeover still need integration. No transcript is copied to the issuer by these interfaces. Task owners retain their existing current-access Task reads; sharing results needs an approved projection.

The PostgreSQL integration checks verify different issuer/executor identities, exact Task replay, Runtime reconstruction, actual tool effects, payer-budget settlement, missing-resolver pause and recovery, issuer cancellation after executor access is removed, and result polling respecting the grant call ceiling. They use deterministic models and service reconstruction, not new real-model or full-process crash evidence.
