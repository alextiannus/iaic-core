# Delegated operation receipts and takeover

For direct external function-grant calls, use [TOOLS.md](TOOLS.md). Their original
attempt receipts live in the existing delegation store; the Task projection below
remains specific to bound Runtime Tasks.

`DelegationProgress({grants, authorizeShare})` reads the original delegated Task's current operation metadata. Its explicit sharing port receives `{action:'progress', ownerActor, recipientActor, grant, revoked}` and must check current policy. Both participants still need current grant read access. Execution revocation does not erase responsibility for previously admitted effects: the host may separately permit progress sharing after revocation. This does not restore artifact, execution or result sharing.

`read(actor, grantId)` returns Task status and at most 1,000 operation receipts, each containing `effectKey`, `capability`, `effect` and `status`. It verifies the original Task's grant digest and exact input. The default TaskStore reads only these columns; no model history, arguments, results, error text or artifact bodies are shared. Alternate stores implement the scoped `operationReceipts(actor, taskId)` port. Oversized or malformed projections fail instead of silently truncating.

Set `CrossPrincipalDelegations.progress` to this module to include fresh receipts in the parent context. Missing configuration is labelled `not_configured`; denied sharing becomes `unavailable`, with no cached receipts. `createDelegationProgressCapability({progress})` supplies an optional read Capability for the same dispatcher and its existing SDK/HTTP/MCP adapters. Revalidation checks current sharing again. The capability is not automatically added to any Agent's tool scope.

For interrupted or cancelled work, the parent can query the original domain effect by its original identifier using its own currently authorized read Capability. It then continues only the remaining work and passes its original outcome verifier. No execution, budget, grant or model history is transferred. This module does not create retries, compensation or another executor.

`requiresReconciliation` is a conservative hint when a write receipt is not succeeded, including a failed write: failure does not establish that nothing happened. A succeeded receipt establishes that its call returned successfully, not that the parent goal is complete. A false hint, an empty receipt list, cancellation, or a Task's terminal status does not guarantee that no external effect is still in flight. These are live observations, not a distributed snapshot or a replay authorization. Domain queries/compensation and any current write preconditions remain application capabilities. Trusted existing Runtime reconciliation can update an unknown original call after obtaining evidence; it must never fabricate success to clear a wait.

Integration evidence uses two principals, the shared Runtime and real PostgreSQL effects. A worker either loses its response after committing an effect or fails to continue after a successful write; the issuer cancels it, services reconstruct, and the parent queries the original effect and independently verifies one stored record. No second write occurs. Evidence also checks denied sharing, revoked-grant progress policy, unrelated-principal rejection and refreshing a reconciled unknown receipt. Models and injected failures are deterministic; real-model and process-kill collaboration acceptance remain outstanding.

Additional process evidence now covers an actual child-worker SIGKILL after the domain write and artifact commit, before returning the call. A separate Runtime reconstructs the original unknown receipt, then the issuer cancels and the parent queries the original effect under its own permission. Exactly one write remains; the parent passes its independent outcome verifier. Grant revocation prevents resubmission, the consumed tool/model admission remains original, and the one completed fixture inference costs two platform units with no pending hold. This does not prove arbitrary external-effect termination or additional-write takeover safety; models are deterministic and the parent completes by verifying existing work.
