# Preserve usable model results while usage reconciliation remains pending

## Outcome needed

Separate a usable model result from pending usage evidence. An application explicitly selecting this policy can continue consuming a verified result while a durable, observable billing reconciliation item retains the original request identity and hold. Do not fabricate zero usage, grant more allowance, or infer business success from the existence of a model response.

## Observed behavior or practice

Obsidian note 46 records an Owner product decision: unknown usage alone must not block an otherwise usable business result. In candidate.117, meteredModel unconditionally throws USAGE_RECONCILIATION_REQUIRED after a resolved provider response without usage; hasPendingTask subsequently blocks the entire Task. Runtime turns this into a waiting state. The local deterministic reproduction below confirms that behavior; it does not establish that the original production provider actually returned a usable result.

## Why this belongs in Core

The unconditional coupling lives in Core billing/metered-model.js and agent/runtime.js. Hosts cannot correctly fix it by inventing usage, mutating ledger records, or retrying provider calls. This is reusable model/ledger orchestration rather than a 12Eat business rule.

## Expected reusable behavior

Represent result availability independently from confirmed/pending usage and expose a stable reconciliation reference. Preserve original Task/turn, model/profile, provider reference, payer/scope, diagnostic and reservation. Runtime still validates actions and enforces all current authorization, domain and budget limits. A persisted pending item remains closable by an authorized billing worker without rewriting the original Task outcome. Continuation policy must not bypass unsettled reservation accounting or permit unbounded new credit. No usable result, indeterminate transport outcome, or explicitly selected fail-closed policy must not be treated as a successful response. Only trusted pre-inference rejection evidence permits providerNotCalled release; an arbitrary status code alone is insufficient.

## Reproduction and evidence

Validated against implementation 005045045fdb306357215808f3947f842b6225f7 / main 015f602f90ee46fe7f7435faf1b1970785878a42, candidate.117. Run from the Core repository with Node 20:

```js
import assert from 'node:assert/strict';
import {meteredModel} from './billing/metered-model.js';
let unknown=0, settled=0, calls=0;
const ledger={hasPendingTask:async()=>unknown>0,reserve:async()=>{},release:async()=>{},markUnknown:async()=>{unknown++;},settle:async()=>{settled++;}};
const model=meteredModel({model:{name:'fixture',next:async()=>{calls++;return {type:'finish',result:{answer:'verified fixture'}};}},ledger,scope:{scopeId:'fixture',subjectId:'fixture'},policy:{maximum:10,price:{input:1,output:1}}});
for(let turn=1;turn<=2;turn++)await assert.rejects(model.next({billingContext:{taskId:'fixture-task',turn}}),{code:'USAGE_RECONCILIATION_REQUIRED'});
assert.equal(calls,1);assert.equal(unknown,1);assert.equal(settled,0);
```

Observed: one resolved provider fixture call, one unknown hold, no settlement; both invocations reject. No network, real provider, production Task or financial mutation was used. Database durability, crash/replay of retained results and a future fix are Not verified.

## Current application workaround

Host readiness checks, trusted pre-dispatch release, visible error reporting and issue tracking. No fabricated tokens or ledger override is accepted as a workaround.
