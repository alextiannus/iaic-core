# Agent identity and responsibility

`AgentIdentityStore` owns persistent work identities and append-only lifecycle revisions. `AgentRegistry` combines that store with application-defined jobs/responsibilities and injected application identity/authorization. `agentIdentityTools` provides headless tool adapters. This module provides neither login accounts nor UI, service credentials, a dynamic plugin market or a second Runtime.

Definitions have `id`, `purpose`, and responsible Agent capability names. `role` is an optional descriptive label (absent becomes null), with no required classification. Existing labels and definition hashes are preserved. Their normalized content is SHA256-versioned. Role names describe work; they confer no permission. Application capability authorization remains mandatory. `resolveScope(actor,definitionId)` must authenticate the caller and return trusted `applicationId/subjectId`; never take these from model input. The host may map existing human or service principals. State changes additionally require `authorizeStateChange`.

`describe(actor,id)` returns the definition and optional instance. The first authorized task binding creates the instance atomically; mere discovery does not. `bind(actor,id,capability)` returns an immutable Task snapshot. `check(actor,binding,capability)` resolves current ownership, definition revision and active state. `setState(actor,id,{state,expectedRevision})` changes active/paused state with optimistic concurrency, recording a revision in the same SQL statement. `history(actor,id,{after,limit})` pages lifecycle changes. State events inherit the instance's application/subject ownership; this is not a signed audit or a delegated-admin attribution system.

TaskStore owns a nullable `agent` snapshot plus its created event. Runtime uses injected `agentIdentity.bind/check` hooks, adds that snapshot to model context, and passes it to `resolveModel` so an application may choose per-Agent settings. The Agent module never reads Task tables; TaskStore never reads identity tables. Existing applications can omit the hooks and retain unbound legacy behavior. A bound Task cannot execute without its identity resolver. Enabling identity enforcement does not fabricate bindings for historical tasks; use their original compatible release or create explicitly new work.

Runtime checks before inference and after responses/before tool admission. Pause prevents new admission once observed; an already admitted model call or external action may finish and its usage/result remains recorded. Pause is not rollback or cancellation. Waiting tasks retain their original identity and require explicit resume after reactivation. Cancellation/read/audit remain available while paused. Definition changes do not rewrite old task responsibilities or bypass existing release-version compatibility rules.

## Application job configuration

`register(definition)` adds a job after construction; the constructor accepts `definitions:[]` or an application-loaded list. `register(definition,{expectedRevision})` replaces the current definition only when its hash matches. It returns the immutable normalized definition, including its `revision`. The optional `configuration` field holds up to 16 KiB of JSON object data; keys are canonicalized and arrays retain order. It is part of the definition hash, so changed resource selections cannot silently rewrite an old Task's binding. `check` rejects the old binding; create new work or retain the original compatible configuration for the original task. Identical configuration loaded from application storage retains its revision. Configuration is not included in the model binding; purpose and optional role remain there.

This is a **trusted host API**, not a model tool or unauthenticated management endpoint. Applications authenticate configuration changes, validate resource references against installed capabilities/Skills, persist configuration and distribute it to workers. The revision comparison covers this registry instance; it is not a distributed transaction or a new Core configuration database. Store only data and resource references here, never secrets or executable code. Existing execution code still follows the application's development/release process.

Core does not interpret configuration keys or build business roles. The host routes existing modules with `registry.definition(id).configuration`: Memory/Workspace scope, selected installed Skills, authorized Knowledge, allowed capabilities, model settings and proactive tasks use their existing APIs. Model credentials and allowance records stay in their owning modules. Default long-lived application scope should distinguish user plus organization; an explicitly shared organization job can map members to the same Agent/resource scope. Personal preference reuse and company source sharing remain explicit host policy. Task actor codecs must preserve the job selection needed for worker recovery.

`examples/core-configurable-jobs` demonstrates that composition using one shared work capability and Runtime. Applications do not need a new capability namespace or a new runtime per job. It loads host-owned JSON after Runtime initialization and executes personal work in two organizations plus a shared editorial job with selected Skills, Knowledge, memory, artifacts, persisted model settings and platform allowance. The example's `shared`, `skills`, `knowledge` and `tools` keys are application choices, not mandatory framework fields. Sessions, mandates and proactive schedules remain separate existing modules; registration alone does not create them.

ImmediToday continues to use its existing internal User Assistant configuration. External Codex remains a valid Platform AI; Core does not require an internally provisioned Platform AI or three-role deployment before use or open-source delivery. Business AI represents system responsibility; User AI represents user/organization responsibility and can also perform long-running work. Concrete application job design belongs to application developers.
