# Explicit task model routing

`AssistantModelRouting({models,resolvePolicy,availability})` composes an existing `AssistantModels` instance. Pass `request => router.resolve(request)` as the existing Runtime `resolveModel` port. It adds no model provider, ledger, Task store or UI.

`resolvePolicy({actor,agent})` must return a currently authorized `{revision,profileIds}` with 1–16 distinct ordered profile IDs, or deny. It is trusted host code: authorize the user/Agent's use of this explicit routing policy, including each alternate provider's data destination. Policy identifiers and choices must not come from model output. The first ID must match the user's selected profile for a new Task. All candidates must exist in that actor's model catalog and use the same credential mode. Cross-model routing is opt-in through this port; ordinary `AssistantModels` behavior is unchanged. A single candidate disables alternatives.

`availability({actor,agent,profile})` returns `available` or `unavailable` from the host's current health/maintenance view. An unknown value or exception stops selection. Availability is advisory, not a concurrency reservation, authorization grant or proof of zero cost. Per-provider `capacityModel` admission still belongs inside each provider's metered gateway. No provider is called to probe availability.

The first available candidate is resolved through `AssistantModels.target`, preserving the actual profile name, model, metering and rate policy. The identity must still match the catalog after resolution. The Runtime persists that real identity in the Task. When resuming with `modelIdentity`, the router resolves only the original authorized identity, irrespective of changed availability/default preference. A removed or revised profile stops work; it never substitutes another model. The returned `routing` metadata describes the resolution policy revision; it is not a separate durable routing journal.

Current catalog identity and routing permission are rechecked before each model call. Removing the candidate or revoking policy stops subsequent calls before billing/provider dispatch. As with other authorization ports, this cannot undo an already in-flight request, and the host must keep policy/scope resolution current.

No error from `next()` triggers another candidate: exhausted allowance, BYOK errors, provider rate limits, capacity rejection, completed invalid actions, unknown usage and transport failure stay with the selected gateway and existing Runtime recovery policy. Each selected model is metered independently under its existing rules. BYOK cannot automatically switch to a platform-paid route, nor can exhausted platform allowance trigger BYOK. This avoids losing attribution or evading an unknown request by selecting a different pool.

Tests compose the real AssistantModels metering wrapper; the installed example also uses PostgreSQL Tasks/ledger and reconstructs Runtime after routing before execution. The old Task retains its backup model while a fresh Task selects the newly available primary. Availability/providers are fixtures, not real vendor failover or process-kill evidence. No automatic health monitor, latency/cost optimizer, RPM/TPM limiter, fair queue or post-dispatch fallback is provided.
